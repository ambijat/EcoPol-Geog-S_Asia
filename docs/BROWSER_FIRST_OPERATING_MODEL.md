# Browser-First Operating Model

The browser cockpit is the main place for instructor review and decisions.

## Use the browser for

- choosing lectures and clusters;
- reviewing historical-slide thumbnails and extracted text;
- reviewing source profiles;
- reviewing knowledge units and alternative patterns;
- comparing old and proposed slides;
- rehearsing a cluster;
- recording returns or acceptance;
- seeing decisions that still require attention.

The browser uses shared course records. A decision recorded in the browser is not a separate browser-only decision.

## Use the Qt sidecar for

- inspecting protected local files;
- converting ODP or PPTX files;
- running LibreOffice locally;
- generating PDFs and thumbnails;
- opening local folders;
- working offline when native desktop access is required.

Qt does not maintain a second academic record. It is a companion for operations that require local desktop access.

## Privacy

The browser workspace uses identifiers and symbolic locations. It does not display physical historical-repository paths in the normal view.

The cockpit should remain locally hosted or access-controlled. Historical source files, unpublished notes, rehearsal records and instructor comments remain local.

## Current boundary

Only Lecture 1A KC01 is active. The other Lecture 1A clusters are visible but locked. Lecture 1B is outside the current workspace.

## External-AI update bridge

The Slide 3 pilot can prepare a self-contained update packet after the instructor records an eligible historical-slide action. The browser copies or downloads the packet but never sends it anywhere. A returned YAML draft must be pasted, validated and compared with the inherited slide. The instructor then edits it, applies the change manually and attaches a derivative before accepting or returning the reinforced slide.

Accepting a proposal does not overwrite the historical slide, build a lecture version, publish material or make a canonical record.
